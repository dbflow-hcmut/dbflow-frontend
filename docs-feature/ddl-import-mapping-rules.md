# DDL Import — SQL to Physical Schema Mapping Rules

## Tổng quan

Tính năng **DDL Import** cho phép người dùng dán SQL DDL (Data Definition Language) vào editor để tự động tạo physical schema trên diagram. Parser chuyển đổi các câu lệnh `CREATE TABLE`, `ALTER TABLE`, và `CREATE INDEX` thành `PhysicalModelPayload` — cấu trúc dữ liệu nội bộ của DBFlow.

**File implementation:** `src/components/EditProject/utils/ddl-parser.ts`

---

## Quy trình xử lý (Pipeline)

```
SQL DDL text
    │
    ▼
┌─────────────────────┐
│  1. Strip Comments   │  Loại bỏ -- và /* ... */
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│  2. Parse CREATE     │  Regex extract từng CREATE TABLE statement
│     TABLE            │
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│  3. Split Body       │  Tách phần body bằng comma (top-level only)
└─────────┬───────────┘
          ▼
┌─────────────────────────────┐
│  4. Classify Each Part       │
│  ├─ PRIMARY KEY constraint   │
│  ├─ FOREIGN KEY constraint   │
│  ├─ UNIQUE constraint        │
│  └─ Column definition        │
└─────────┬───────────────────┘
          ▼
┌─────────────────────┐
│  5. Parse CREATE     │  Standalone CREATE [UNIQUE] INDEX
│     INDEX            │
└─────────┬───────────┘
          ▼
┌─────────────────────────────┐
│  6. ID Assignment (Pass 1)   │  generateId() cho mỗi table & column
└─────────┬───────────────────┘
          ▼
┌─────────────────────────────┐
│  7. FK Resolution (Pass 2)   │  Map tên bảng/cột → ID đã gán
└─────────┬───────────────────┘
          ▼
    PhysicalModelPayload
```

## Chi tiết Mapping Rules

### 1. Comment Handling

| SQL Input | Hành vi |
|-----------|---------|
| `-- single line comment` | Loại bỏ hoàn toàn |
| `/* multi-line comment */` | Loại bỏ hoàn toàn |

### 2. Identifier Quoting

Parser hỗ trợ 3 kiểu quote identifier:

| SQL Input | Kết quả |
|-----------|---------|
| `"my_table"` | `my_table` (double-quote, PostgreSQL/SQL standard) |
| `` `my_table` `` | `my_table` (backtick, MySQL) |
| `[my_table]` | `my_table` (bracket, SQL Server) |
| `my_table` | `my_table` (không quote) |

### 3. CREATE TABLE → `ModelTable`

```sql
CREATE TABLE [IF NOT EXISTS] table_name ( ... );
```

**Mapping:**

| DDL | PhysicalModelPayload | Ghi chú |
|-----|---------------------|---------|
| `table_name` | `table.name` | Unquoted |
| _(auto)_ | `table.id` | `pid_<uuid>` format |

### 4. Column Definition → `ModelColumn`

```sql
column_name DATA_TYPE[(length)] [NOT NULL] [UNIQUE] [PRIMARY KEY] [DEFAULT value] [AUTO_INCREMENT] [REFERENCES ...]
```

**Mapping chi tiết:**

| DDL Clause | `ModelColumn` field | Giá trị | Ghi chú |
|------------|-------------------|---------|---------|
| `column_name` | `name` | Tên cột (unquoted) | |
| `DATA_TYPE` | `dataType` | Uppercase (e.g. `VARCHAR`, `INTEGER`) | Luôn chuyển thành uppercase |
| `(length)` | `length` | String (e.g. `"255"`, `"10,2"`) | Giữ nguyên giá trị trong ngoặc |
| `NOT NULL` | `nullable` | `false` | Mặc định `true` nếu không có `NOT NULL` |
| _(không có NOT NULL)_ | `nullable` | `true` | |
| `UNIQUE` | `unique` | `true` | Mặc định `false` |
| `PRIMARY KEY` (inline) | `roles.primaryKey` | `true` | Cũng set `nullable = false` |
| `DEFAULT value` | `defaultValue` | String value | Bỏ quote nếu là string literal |
| `AUTO_INCREMENT` | `autoIncrement` | `true` | MySQL syntax |
| `AUTOINCREMENT` | `autoIncrement` | `true` | SQLite syntax |
| _(auto)_ | `id` | `pid_<uuid>` | |

### 5. Auto-Increment Detection

Parser nhận diện nhiều syntax auto-increment khác nhau:

| DBMS | SQL Syntax | Mapped `dataType` | `autoIncrement` |
|------|-----------|-------------------|-----------------|
| MySQL | `INT AUTO_INCREMENT` | `INT` | `true` |
| SQLite | `INTEGER AUTOINCREMENT` | `INTEGER` | `true` |
| PostgreSQL | `SERIAL` | `INTEGER` | `true` |
| PostgreSQL | `BIGSERIAL` | `BIGINT` | `true` |
| PostgreSQL | `SMALLSERIAL` | `SMALLINT` | `true` |
| SQL Standard | `INT GENERATED ALWAYS AS IDENTITY` | `INT` | `true` |
| SQL Standard | `INT GENERATED BY DEFAULT AS IDENTITY` | `INT` | `true` |

> **Quan trọng:** `SERIAL`, `BIGSERIAL`, `SMALLSERIAL` là shorthand của PostgreSQL, parser tự động chuyển sang data type thực (`INTEGER`, `BIGINT`, `SMALLINT`) và bật `autoIncrement`.

### 6. Primary Key → `roles.primaryKey`

#### 6.1. Inline Primary Key

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY
);
```

→ Column `id`: `roles.primaryKey = true`, `nullable = false`

#### 6.2. Table-level Primary Key (đơn & composite)

```sql
CREATE TABLE order_items (
    order_id INTEGER,
    item_id INTEGER,
    PRIMARY KEY (order_id, item_id)
);
```

→ Cả `order_id` và `item_id`: `roles.primaryKey = true`, `nullable = false`

#### Quy tắc merge

- Nếu cột vừa có inline `PRIMARY KEY` vừa xuất hiện trong table-level `PRIMARY KEY(...)`, kết quả giống nhau: `primaryKey = true`.
- Collection `primaryKeyColumns` chứa tên tất cả PK columns, merge từ cả 2 nguồn.

### 7. Foreign Key → `roles.foreignKey`

#### 7.1. Inline References

```sql
CREATE TABLE posts (
    user_id INTEGER REFERENCES users(id) ON DELETE CASCADE ON UPDATE NO ACTION
);
```

**Mapping:**

| DDL | `ModelColumn.roles.foreignKey` field |
|-----|-------------------------------------|
| `users` (referenced table) | `refTableId` → ID của table `users` |
| `id` (referenced column) | `refColumnId` → ID của column `users.id` |
| `ON DELETE CASCADE` | `onDelete: "CASCADE"` |
| `ON UPDATE NO ACTION` | `onUpdate: "NO ACTION"` |

#### 7.2. Table-level FOREIGN KEY

```sql
CREATE TABLE posts (
    user_id INTEGER NOT NULL,
    CONSTRAINT fk_posts_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

→ Mapping tương tự, `CONSTRAINT name` được bỏ qua (không lưu tên constraint).

#### 7.3. Composite Foreign Key

```sql
FOREIGN KEY (order_id, item_id) REFERENCES order_items(order_id, item_id)
```

→ Mỗi cột trong composite FK được map riêng:
- `order_id.roles.foreignKey.refColumnId` → ID của `order_items.order_id`
- `item_id.roles.foreignKey.refColumnId` → ID của `order_items.item_id`

#### 7.4. FK Actions được hỗ trợ

| SQL Clause | `FKAction` value |
|-----------|-----------------|
| `ON DELETE CASCADE` | `"CASCADE"` |
| `ON DELETE SET NULL` | `"SET NULL"` |
| `ON DELETE SET DEFAULT` | `"SET DEFAULT"` |
| `ON DELETE RESTRICT` | `"RESTRICT"` |
| `ON DELETE NO ACTION` | `"NO ACTION"` |
| _(không có ON DELETE)_ | `undefined` |

Tương tự cho `ON UPDATE`.

#### 7.5. FK Resolution (Two-Pass)

Parser sử dụng **2 lần duyệt** để resolve FK:

1. **Pass 1 — ID Assignment:** Tạo `tableIdMap` (tableName → tableId) và `columnIdMap` (tableName → Map(colName → colId)) cho tất cả tables/columns.
2. **Pass 2 — FK Wiring:** Với mỗi FK, tra cứu `refTableId` và `refColumnId` bằng tên bảng/cột (case-insensitive).

> **Lưu ý:** Nếu bảng/cột tham chiếu không tồn tại trong DDL input, FK sẽ bị bỏ qua (không gây lỗi). Điều này cho phép import partial schema.

### 8. UNIQUE Constraint → `ModelIndex`

#### 8.1. Inline UNIQUE

```sql
email VARCHAR(255) UNIQUE
```

→ `column.unique = true` (flag trên column, không tạo index riêng)

#### 8.2. Table-level UNIQUE

```sql
CONSTRAINT uq_email UNIQUE (email, domain)
```

**Mapping:**

| DDL | `ModelIndex` field |
|-----|-------------------|
| `uq_email` | `name` |
| `email, domain` | `columns: [{ columnName: "email", order: "ASC" }, { columnName: "domain", order: "ASC" }]` |
| _(luôn)_ | `isUnique: true` |
| _(luôn)_ | `type: "BTREE"` |

Nếu không có `CONSTRAINT name`, tên tự động sinh: `uq_{tableName}_{col1}_{col2}`.

### 9. CREATE INDEX → `ModelIndex`

```sql
CREATE [UNIQUE] INDEX [IF NOT EXISTS] index_name ON table_name (col1 [ASC|DESC], col2 [ASC|DESC]);
```

**Mapping:**

| DDL | `ModelIndex` field |
|-----|-------------------|
| `index_name` | `name` |
| `table_name` | _(gắn index vào table tương ứng)_ |
| `UNIQUE` | `isUnique: true` (mặc định `false`) |
| `col1 ASC` | `{ columnName: "col1", order: "ASC" }` |
| `col2 DESC` | `{ columnName: "col2", order: "DESC" }` |
| _(luôn)_ | `type: "BTREE"` |
| _(auto)_ | `id: pid_<uuid>` |

> **Lưu ý:** Nếu `table_name` trong `CREATE INDEX` không tìm thấy trong danh sách tables đã parse, index này sẽ bị bỏ qua.

### 10. DEFAULT Value Parsing

| SQL | `defaultValue` |
|-----|---------------|
| `DEFAULT 0` | `"0"` |
| `DEFAULT 'hello'` | `"hello"` (bỏ quote) |
| `DEFAULT CURRENT_TIMESTAMP` | `"CURRENT_TIMESTAMP"` |
| `DEFAULT NULL` | `"NULL"` |
| `DEFAULT 'it''s'` | `"it's"` (escaped quote) |

## Output Structure: PhysicalModelPayload

```typescript
{
    model: {
        id: "pid_<uuid>",           // Auto-generated
        name: "<diagramName>",       // Từ diagram name hiện tại
        version: 1,                  // Luôn = 1 khi import mới
    },
    tables: [
        {
            id: "pid_<uuid>",
            name: "users",
            columns: [
                {
                    id: "pid_<uuid>",
                    name: "id",
                    dataType: "INTEGER",
                    nullable: false,
                    unique: false,
                    autoIncrement: true,
                    roles: { primaryKey: true },
                },
                {
                    id: "pid_<uuid>",
                    name: "email",
                    dataType: "VARCHAR",
                    length: "255",
                    nullable: false,
                    unique: true,
                    roles: {},
                },
            ],
            indexes: [
                {
                    id: "pid_<uuid>",
                    name: "idx_users_email",
                    type: "BTREE",
                    columns: [{ columnName: "email", order: "ASC" }],
                    isUnique: true,
                },
            ],
        },
    ],
}
```

## Cách ghi vào Diagram

Import sử dụng `physicalMutateModel` (collaboration hook):

```typescript
physicalMutateModel(() => importedModel);
```

- Thay thế **toàn bộ** model hiện tại bằng model import.
- Sau khi mutate, `buildDiagramFromPhysicalModel` tự động tạo ReactFlow nodes/edges với **ELK auto-layout**.
- Tất cả FK relationships sẽ tạo edges nối giữa các table nodes.

## Giới hạn / Limitations

### ✅ Đã xử lý

| Aspect | Chi tiết |
|--------|---------|
| `CREATE TABLE` | Hỗ trợ đầy đủ, kể cả `IF NOT EXISTS` |
| `CREATE INDEX` / `CREATE UNIQUE INDEX` | Hỗ trợ, kể cả `USING` clause và ASC/DESC per column |
| Schema prefix (`public.users`) | Strip tự động — chỉ lấy phần sau dấu `.` cuối cùng |
| Index type `USING HASH/GIN/GIST/BRIN` | Map sang `IndexType` tương ứng; fallback về `BTREE` nếu không nhận ra |
| Duplicate table name | Cảnh báo warning, import tiếp tục với definition cuối cùng |
| FK tham chiếu bảng ngoài DDL input | Báo warning rõ ràng, FK bị bỏ qua có kiểm soát |
| `CREATE INDEX` thiếu dấu `;` | Báo warning trong Monaco editor và Alert panel |

---

### ❌ Không hỗ trợ và lý do chi tiết

#### 1. `ALTER TABLE ADD COLUMN` / `ALTER TABLE ADD CONSTRAINT`

**Lý do không làm:**

Parser hiện tại xây dựng model theo từng `CREATE TABLE` statement — mỗi bảng là một đơn vị độc lập. `ALTER TABLE` yêu cầu **stateful parsing**: phải biết bảng đang tồn tại, tìm đúng bảng đó, rồi merge column/constraint mới vào.

Các edge case cực kỳ phức tạp:
- `ALTER TABLE` có thể đứng **trước** `CREATE TABLE` trong file (e.g. migration script ngược)
- `ALTER TABLE RENAME COLUMN`, `ALTER TABLE DROP COLUMN` — phải track history
- SQL Server dùng `sp_rename` thay `ALTER TABLE RENAME`
- Conflict với duplicate table detection khi có nhiều `ALTER` cho cùng bảng

**Workaround:** Người dùng export full schema (pg_dump với `--schema-only --no-owner`) sẽ chỉ có `CREATE TABLE` + `ALTER TABLE ADD CONSTRAINT` (FK). FK qua ALTER TABLE đã được xử lý bởi parser nếu có, nhưng `ADD COLUMN` thì không.

---

#### 2. `CHECK` constraint

**Lý do không làm:**

`ModelColumn` type hiện tại **không có field nào** để lưu CHECK constraint:

```typescript
type ModelColumn = {
    id, name, dataType, length, nullable, unique,
    autoIncrement, defaultValue,
    roles: { primaryKey?, foreignKey?, candidateKey? }
    // ← không có checkConstraint hay validation field
};
```

Để support CHECK, cần:
1. Thêm field mới vào `ModelColumn` type
2. Cập nhật tất cả places đọc/ghi `ModelColumn` (DDL generator, diagram builder, UI)
3. Thiết kế UI để hiển thị CHECK expression

Đây là thay đổi model lớn, nằm ngoài scope của DDL import.

---

#### 3. `ENUM` type — không parse enum values

**Lý do không làm:**

`ModelColumn.dataType` là một `string` đơn giản — chỉ lưu tên type như `"VARCHAR"`, `"INTEGER"`. Không có field để lưu enum values.

```typescript
// Hiện tại:
{ dataType: "ENUM", length: undefined }

// Để support ENUM values cần:
{ dataType: "ENUM", enumValues: ["active", "inactive", "pending"] }
// → cần thêm field mới vào ModelColumn type
```

Ngoài ra ENUM syntax khác nhau giữa DBMS:
- MySQL: `ENUM('val1', 'val2')` — inline trong column def
- PostgreSQL: `CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy')` — separate statement, referenced by name
- SQL Server: không có ENUM, dùng CHECK constraint thay thế

Parser tên type là `"ENUM"` vẫn đủ để biểu diễn column trên diagram, chỉ thiếu enum values.

---

#### 4. `PARTITION BY`, `TABLESPACE`, `ENGINE=InnoDB`, v.v.

**Lý do không làm:**

Đây là **storage/physical options** — không ảnh hưởng đến logical structure của schema:
- `PARTITION BY RANGE (year)` → chỉ ảnh hưởng cách data được lưu trên disk
- `TABLESPACE pg_default` → chỉ ảnh hưởng storage location
- `ENGINE=InnoDB` → MySQL storage engine

`PhysicalModelPayload` không có chỗ lưu những metadata này, và chúng cũng không hiển thị được trên diagram. Parser hiện tại bỏ qua chúng một cách an toàn — không gây lỗi.

---

#### 5. Column `COMMENT` → `notes`

**Lý do không làm ngay:**

`ModelColumn.notes?: string` có trong type definition, nhưng:
1. **UI không hiển thị** `notes` ở đâu trên diagram node
2. **DDL Export** (`ddl-generator.ts`) không generate `COMMENT ON COLUMN` 
3. Nếu import notes nhưng không thấy được và không export được → gây ấn tượng data bị mất

Khi UI có chỗ để hiển thị column notes (tooltip hoặc panel), có thể thêm:
```typescript
// Cần parse: MySQL — COMMENT 'text', PostgreSQL — COMMENT ON COLUMN
const commentMatch = colDef.match(/\bCOMMENT\s+'([^']*)'/i);
if (commentMatch) notes = commentMatch[1];
```

## Ví dụ End-to-End

### Input DDL

```sql
CREATE TABLE departments (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE employees (
    id BIGSERIAL PRIMARY KEY,
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL,
    email VARCHAR(255) NOT NULL,
    dept_id INTEGER REFERENCES departments(id) ON DELETE SET NULL,
    salary DECIMAL(10,2) DEFAULT 0,
    hire_date DATE DEFAULT CURRENT_DATE,
    is_active BOOLEAN DEFAULT true
);

CREATE UNIQUE INDEX idx_employees_email ON employees(email);
CREATE INDEX idx_employees_dept ON employees(dept_id);
```

### Output Tables

| Table | Columns | PK | FK | Indexes |
|-------|---------|----|----|---------|
| `departments` | `id` (INTEGER, PK, autoIncrement), `name` (VARCHAR(100), NOT NULL, UNIQUE) | `id` | — | — |
| `employees` | `id` (BIGINT, PK, autoIncrement), `first_name` (VARCHAR(50)), `last_name` (VARCHAR(50)), `email` (VARCHAR(255)), `dept_id` (INTEGER, FK→departments.id), `salary` (DECIMAL(10,2), default "0"), `hire_date` (DATE, default "CURRENT_DATE"), `is_active` (BOOLEAN, default "true") | `id` | `dept_id` → `departments.id` (ON DELETE SET NULL) | `idx_employees_email` (UNIQUE), `idx_employees_dept` |
